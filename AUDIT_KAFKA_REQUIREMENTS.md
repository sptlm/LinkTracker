# Аудит проекта по требованиям ДЗ (Kafka + асинхронные нотификации)

Дата аудита: 2026-04-21.

## Краткий итог

- Базовая Kafka-интеграция реализована.
- Реализованы DLQ/retry на стороне Bot и Transactional Outbox на стороне Scrapper.
- Есть Avro + Schema Registry как бонус.
- При этом обнаружены важные несоответствия формальным требованиям задания и несколько архитектурных/операционных рисков.

## Проверка по критериям

### 1) Асинхронная отправка Scrapper -> Bot через Kafka

**Статус:** частично выполнено.

Что есть:
- Транспорт переключается через `app.notifications.transport` и по умолчанию стоит `KAFKA`.
- Для Kafka есть отдельные publisher/consumer реализации и условная активация Spring-бино́в.

Проблемы:
1. По условию базовой части сообщения в очереди должны передаваться в JSON-формате и совпадать с синхронной моделью. В текущей конфигурации по умолчанию выставлен `AVRO` (в обоих сервисах), что противоречит базовому требованию.
2. Модель действительно совпадает (`LinkUpdate`), но формат дефолтного потока не JSON.

### 2) Docker Compose с отказоустойчивым Kafka-кластером (3 брокера + координатор)

**Статус:** выполнено.

Что есть:
- 3 брокера Kafka в режиме KRaft без ZooKeeper.
- Корректно задан `KAFKA_CONTROLLER_QUORUM_VOTERS`.

Замечание:
- Для dev-среды не хватает healthcheck/ожидания готовности у Kafka-брокеров, есть только `sleep 15` перед созданием топиков. Это хрупко и может флакать на медленных хостах.

### 3) Добавлен топик + объяснение настроек

**Статус:** технически выполнено, документирование — частично.

Что есть:
- Топик создается в `compose` (`kafka-topics-init`) и программно через `NewTopic`.
- Проставлены `partitions=3`, `replication-factor=3`, `min.insync.replicas=2`.

Проблемы:
1. Неочевидное дублирование создания топика двумя механизмами (compose + Spring Admin). Это может приводить к "дрейфу" конфигурации между окружениями.
2. В проекте нет явного, централизованного объяснения выбора параметров топика для проверки ДЗ (в README есть перечисление, но не обоснование как отдельный блок критерия).

### 4) Тесты + Testcontainers + интеграционный тест Scrapper -> Kafka -> Bot

**Статус:** в целом выполнено.

Что есть:
- Набор интеграционных тестов с Kafka Testcontainers для publisher/consumer.
- Есть сквозной тест Scrapper -> Kafka -> Bot (`ScrapperKafkaToBotIT`).
- Проверены сценарии DLQ/retry.

Риск/недочет:
- Тесты в разных классах поднимают отдельные `KafkaContainer` экземпляры (а не единый контейнер на весь тест-сьют), что ухудшает время и стабильность CI вразрез с рекомендацией задания.

## Проверка дополнительных заданий

### A) Retry + DLQ в consumer

**Статус:** выполнено.

Что есть:
- `DefaultErrorHandler` + `DeadLetterPublishingRecoverer`.
- `maxAttempts` вынесен в конфиг.
- Ошибки десериализации/валидации помечены как non-retryable и сразу уходят в DLQ.

Нюанс:
- DLQ-топик создается с replication factor = 1, что слабее основной идеи отказоустойчивости кластера.

### B) Transactional Outbox

**Статус:** частично выполнено (рабочая реализация, но не полностью production-grade).

Что есть:
- Таблица outbox, отложенная публикация, диспетчер, фиксация SENT только после отправки.

Проблемы/риски:
1. Нет верхней границы попыток и terminal-state (например, `FAILED`), значит "ядовитые" события будут ретраиться бесконечно.
2. Нет claim/lock-механизма для конкурентных диспетчеров (`SELECT ... FOR UPDATE SKIP LOCKED`), что может приводить к дублям при масштабировании.
3. Нет явной идемпотентности на стороне Bot, хотя в советах к ДЗ это отмечено как важный аспект для outbox-схемы.

### C) Avro + Schema Registry

**Статус:** выполнено как бонус.

Замечания качества:
1. Реализация Avro-кодека дублируется почти 1-в-1 в `bot` и `scrapper` (технический долг).
2. В кодеке при `IOException` тоже вызывается `Thread.currentThread().interrupt()`, хотя прерывания не было. Это некорректный паттерн обработки исключений.

## Конкретные рекомендации (приоритет)

1. **Высокий приоритет:** вернуть дефолтный Kafka payload в `JSON` для соответствия базовому требованию, Avro оставить как opt-in.
2. **Высокий приоритет:** выбрать один источник правды для создания топиков (либо compose init, либо Spring Admin) и зафиксировать это в документации.
3. **Средний приоритет:** усилить outbox:
   - `max_attempts` + статус `FAILED`;
   - выборка с блокировкой (`FOR UPDATE SKIP LOCKED`);
   - идемпотентная обработка на стороне Bot.
4. **Средний приоритет:** DLQ replication factor поднять минимум до 3 (или конфигурировать под окружение).
5. **Средний приоритет:** убрать дублирование Avro-кодека (вынести в `contract`/общий модуль).
6. **Низкий приоритет:** заменить `sleep 15` в инициализации топиков на readiness/health-ориентированный сценарий.
